# Architecture and contributor rules

Read this file and PROJECT_STATUS.md before resuming work. Communicate with the operator in Turkish; identifiers and primary developer documentation use English.

## Runtime and boundaries

Use strict TypeScript ESM, Node 24 LTS, discord.js v14 and pnpm. One application process owns one SQLite database/token. No HTTP server, dashboard, external queue or database service.

- src/contracts.ts defines Store, SecurityEvent, Incident, EnforcementAdapter, SecurityProcessor and BackupService.
- configuration validates environment, persisted settings and trusted-principal records with Zod.
- database implements prepared SQLite statements, schema migration versions and atomic claimIncident. Every data and dedupe key is guild-scoped.
- security owns module metadata, correlation, whitelist evaluation, counters and policy decisions. Keep Discord APIs out of this layer.
- discord owns interaction acknowledgement/authorization, native components, audit normalization/fallback, enforcement adapters and delivery of logs.
- recovery owns validated structural snapshots, operation journals, ID mappings and conservative reversal. Reuse authoritative fetch results, not stale manager caches.
- restart owns planned-maintenance role-permission snapshots, checksummed plans and per-effect journals. Never strip managed/bot-held roles or permissions Guard cannot grant back. Keep decimal masks, current-state conflict checks and shared recovery locking. Restore only recorded effects while healthy effective Protect is installed; Monitor or missing recovery dependencies retains lockdown. Never repeat uncertain requests or restore privileges to contained principals. Cancel after locking cannot bypass restore confirmation.
- index coordinates startup, health, periodic maintenance and orderly shutdown.
- logging owns safe process-language console formatting and optional asynchronous bounded JSON diagnostics. startup owns one coordinated readiness report and per-guild startup notification, independent from reconnects. Failed optional features never stop security; critical database failure stops startup explicitly.
- control owns immutable BOT_OWNER_ID authorization, actor-bound management repositories, source-configured global bot profile and per-guild voice state. Automatic engine/recovery maintenance uses the original repositories independently of management authorization.

Guard modules expose id, auditActions, severity and recovery metadata plus per-guild ModuleConfig. Extend the registry and normalizer together, with regression tests. New modules default to monitor/log. Distinguish ordinary role edits from critical permission grants, including initial role creation and role assignments.

## Mandatory security rules

Never infer who kicked a member from member departure. Use authoritative audit identities, exact action/target matching and bounded time windows. Ambiguous or missing attribution produces an unresolved incident without punishment. Dedupe using durable IDs. Persist decisions before external effects; never replay uncertain crash-interrupted effects automatically.

Owner-only configuration and restore confirmation are intentional. Administrator visibility does not authorize management. Check immutable BOT_OWNER_ID authorization before every management route and at each service boundary; bind private workflow sessions to user, guild, expiration and one-use confirmations. Persistent public controls validate the registered guild/channel/message and current bot author on every route; navigation cannot depend on an expiring in-memory session. Acknowledge interactions before network requests; opening a modal requires its own immediate acknowledgement.

Never punish the actual guild owner, configured BOT_OWNER_ID or bot self-actions. Management ownership and whitelist remain independent. Fetch fresh member/role data for whitelist, hierarchy and live-state reversal checks. Recheck settings and whitelist before effects. Missing security dependencies fail closed. Respect permissions and REST rate handling. Never remove unrelated harmless roles. Ban keeps messages.

The owner-confirmed zeroTolerance profile is centralized in control/protection.ts: all eligible administrative modules act on the first confirmed event. Module flags/thresholds cannot weaken this profile; individual preferences remain saved. Invite/thread participation and raids stay observations only. protectionActivatedAt prevents punishing delayed Monitor events. Monitor cancels pending activation and stops further automatic effects. Keep legacy selective behavior compatible until explicit activation.

Contain before rollback. Separate bounded rollback and notice queues from detection/containment. Check effective permissions, fresh roles, everyone/member/channel overrides and hierarchy; incomplete containment is critical. Never rearm a contained executor through membership/shared-role restoration. Rollback must re-fetch exact audit evidence, refuse later target changes, recheck authorization before effects and journal all uncertain API effects. Manual and automatic structural restores share acquireRecoveryOperation.

Only validated known_good_snapshots metadata/checksums authorize automatic structural recovery. Reuse existing trusted state on mode reactivation; never replace it with live unreviewed state. Advance only exact trusted old-to-new fields. Preserve the latest valid baseline during retention and quarantine suspect post-incident data. Keep migration 3 non-destructive; no automatic uncertain-effect replay.

Restore is additive/update only and may be partial. Deleted objects receive new IDs. Preserve overwrite/parent references, and refuse missing dependencies instead of silently removing restrictions. Journal pending creates before APIs and stop uncertain repeats. Manual restore requires preview and explicit owner confirmation. Automatic reverse only edits audited fields when fresh live state still matches the audited new values.

No secrets in code, fixtures, logs or Git. Do not execute destructive live tests or publish/push without explicit operator authorization. A passing mock suite is not live Discord verification.

Use createLogger in both runtime modes; pretty/tr/info defaults and NO_COLOR are intentional. Console language is independent from guild language. Keep structured diagnostic facts while deriving visible Safe/Monitor/Mitigated/Failed from security/activity.ts. File logging must be bounded, redact secrets before output and isolate failures. Resolve relative data/log paths against project root for source and compiled execution. Do not reset a database after migration failure. Startup coordinator owns presence/voice/panel initialization; do not add competing ready notification listeners. Panel start is cached once per process. Default missing-panel recovery stays manual; an explicitly saved recoveryBehavior replace permits one definitive10008 replacement through the existing creation journal. Uncertain sends are never blindly retried.

## Collaboration and verification

File ownership must be explicit before parallel agents edit. Typical owners: lead (contracts, runtime, database, integration/docs), security engineer (security/tests), Discord engineer (discord/tests), recovery engineer (recovery/tests). Shared-interface changes require coordination. Stage child changes in the writable chat work directory if repository permissions are unavailable; lead integrates and checks them.

Use Prettier, ESLint and strict compiler checks. Run pnpm typecheck, pnpm lint, pnpm test and pnpm build after integration. Add meaningful security regressions rather than implementation-mirroring tests. Local tests use mocks/temporary databases. Keep docs honest about implemented, unsupported and unverified behavior. Update PROJECT_STATUS.md with results, limitations, affected files and the exact next steps before ending a session.

## Discord UX and localization conventions

The official /guard panel transport is permanent-router.ts + permanent-panel.ts. One registered channel message per guild is public and survives restart. Public navigation uses versioned durable IDs and persisted view state; sensitive details/one-use confirmations stay private. Never let public control validity depend on Sessions expiry. Check guild/channel/message/current author and immutable BOT_OWNER_ID on every public interaction. Contextual module IDs include a view signature. Refresh the same message with advisory change events, debounce and payload dedupe; never let optional UI updates block security writes. On restart restore overview, mark missing references unavailable, and require an owner command to recreate. Pin/move target only the registered message; do not alter unrelated pins. Migration 4 preserves all existing data.

The simplified whitelist command tree is `/guard whitelist add subject:<ID>`, `/guard whitelist remove subject:<ID>`, `/guard whitelist list`. Never restore operation/kind/module-list arguments to the default command. Resolve current-guild roles before members; identify bots explicitly. API failure must not become a guessed trusted identity. New grants use actions ["*"] with no expiry; this all-module access must be explicit in the success view. Preserve old entry IDs, scopes and expiry until the operator explicitly upgrades/removes that subject. Revalidate BOT_OWNER_ID authorization after asynchronous subject lookup immediately before saving a new grant. Scoped or expiring grants require a separate upgrade confirmation.

Keep advanced whitelist evaluation in the existing Security Engine. UI simplification must not change attribution, permission hierarchy, monitor defaults, enforcement policy or restore safety.

src/configuration/bot-profile.ts is the sole profile source. Ignore obsolete SQLite presence records without deleting them; never restore a profile editor in Discord. Presence uses supported bot Activity fields only; reject custom emoji rather than claiming it was applied. Application description uses ClientApplication.fetch/edit with the documented 400-character validation and compare-before-write; only one startup sync attempt, no timer. API/config failures must not stop security, and manual Developer Portal fallback must be documented. Voice uses @discordjs/voice with GuildVoiceStates and ViewChannel/Connect checks, one connection per guild and bounded retries. Persist manual disconnect across restart; only explicit connect/reconnect or enabling auto-join clears the pause. Do not add audio playback/recording or make security depend on voice availability. Reset preserves runtime records and active emergency verification; its separate confirmed control restores the saved platform verification level.

Use src/locales for all visible interface text and metadata helpers for native command localizations. GuildConfig.language defaults to tr when absent; en is an explicit persisted choice. Native slash metadata follows Discord client locale, while response language follows guild configuration. These systems are independent. Keep catalog keys complete in both languages, interpolate values safely and avoid inherited-object translation keys.

All user-facing embeds use src/discord/embeds.ts for colors and the localized Casi footer. Discord-facing exceptions use UserError keys; raw errors/stacks belong in local logs. Saved technical incident/recovery results are translated by presentation helpers without rewriting old records. Keep structured diagnostic facts in their technical form; console presentation has its independent TR/EN setting. Do not repeat branding on buttons.

Activity classification lives in security/activity.ts and the reusable Discord log builder/delivery in discord/security-log.ts. Safe requires confirmed executor plus a verified exemption; metadata is assigned only in existing engine trust branches. Safe records remain stored but are excluded from hostile counts/pages. Do not confuse queued/sent requests, zero removed roles or unknown legacy output with actual mitigation. Preserve enforcementAttempted and resolved rollback effectsApplied evidence. Pending/final audit outcomes update one persistent mapped bot-authored log message; uncertain sends never replay blindly. Public recent activity uses colored indicators without exposing confidential identities. Keep all action/reason/status/native-command strings in the same TR/EN catalog system, with exact key/placeholder parity tests.

/guard limits and /guard modules open friendly, paginated protection selectors; no manually typed module IDs. Numerical limits use modals with clear whole-number validation. Optional raid features remain monitoring-only in every view. Keep real health/counts accurate and verify component/embed limits and acknowledgements in both languages.

The runtime and emergency recovery CLI acquire SqliteStore.acquireProcessLease before login; never run both against the same file. Keep Compose hostname stable and process-generation checks for container PID reuse. Do not bypass a live or foreign-host lease. CLI preview reads current roles; explicit --confirm SESSION_ID authorizes only the active recorded session. Confirmed recovery keeps the real Guard engine online until operator shutdown. Ordinary private component navigation uses deferUpdate on that private message; modal submissions stay private and never update a public message accidentally. All ordinary /guard routes bridge canonical state; never reintroduce full ephemeral main-panel copies. View revisions reject obsolete async publications.
